1. 概要

日々の歩数・睡眠時間・体重・食事内容を記録し、内容から算出した「健康スコア」で自分の生活習慣を振り返るためのシングルページアプリケーション。

データ保存は2モードあり、ビルド時の環境変数 VITE_API_BASE_URL で切り替わる:

  • API保存モード(設定あり): Express + PostgreSQL のバックエンド(server/)にREST APIで保存
  • localStorageモード(未設定): サーバーを持たず、すべてのデータをブラウザの localStorage に保存
  • データの持ち出し・復元は手動のJSONエクスポート/インポートで行う(モード間の移行にも使える)

4. データモデル

フロントエンドが扱うデータ形式は両モード共通。保存先だけが異なる。

モード記録の保存先プロフィールの保存先
API保存PostgreSQL records テーブルPostgreSQL profile テーブル(常に1行、id = 1)
localStorageキー health-app-recordsキー health-app-profile

4.1 記録 (Record)

日付ごとに1件。localStorageモードでは配列としてJSON保存される。

フィールド型必須説明
idstring (UUID)○crypto.randomUUID() で採番
datestring (YYYY-MM-DD)○記録日。同日の記録は上書きされる(1日1件)
stepsstring (数値)任意歩数
sleepHoursstring (数値)任意睡眠時間(h)
weightstring (数値)任意その日の体重(kg)。未入力時はプロフィールの体重を評価に使用
mealMemostring任意食事の自由記述メモ

DBの records テーブルでは各フィールドをsnake_case(sleep_hours, meal_memo)で保持し、date に UNIQUE 制約を張ることで「1日1件」をDBレベルでも保証する。テーブルはサーバー起動時に CREATE TABLE IF NOT EXISTS で自動作成される。

weightstring (数値, kg)基本体重。日次記録に体重未入力の場合のフォールバック値

5. 健康スコアのロジック

各記録について、以下4項目をそれぞれ0〜100点で算出し、加重平均で総合スコア(0〜100、四捨五入)を出す。入力がない項目は計算対象から除外され、残りの項目だけで加重平均を取り直す(全項目未入力の場合は null)。

項目重み未入力時の扱い
歩数30%除外
睡眠時間30%除外
体重20%除外(身長未設定 or 体重情報なしの場合)
食事20%0点として計算(食事メモなし=0点は必ず加算)

5.1 歩数スコア

score = min(歩数 / 10000, 1) × 100

1万歩で100点、以降は頭打ち。

5.2 睡眠スコア

  • 7〜9時間: 100点
  • 7時間未満: (睡眠時間 / 7) × 100
  • 9時間超: 100 - ((睡眠時間 - 9) / 9) × 100(下限0点)

5.3 体重スコア

  1. プロフィールの性別・身長からBMI基準の適正体重を算出
    • 理想BMI: 男性22 / 女性21 / その他21.5
    • 適正体重 = 理想BMI × (身長m)²
  2. その日の記録に体重入力があればそれを、なければプロフィールの体重を「評価対象の体重」とする
  3. 適正体重との乖離率20%で0点になるように線形減点
diffRatio = |体重 - 適正体重| / 適正体重
score = max(0, 100 - (diffRatio / 0.2) × 100)

5.4 食事スコア(キーワードヒューリスティック)

自由記述の食事メモに対し、あらかじめ定義した食品カテゴリのキーワードが含まれるかで判定する(自然言語・栄養データベースによる厳密な解析ではない)。

  • カテゴリ: 主食・主菜・副菜(各カテゴリに約13〜19個の代表キーワードを保持)
  • 加点: カテゴリごとに、該当キーワードが1つ見つかれば20点、2つ目以降は+5点ずつ(カテゴリ上限25点)
  • バランスボーナス: 主食・主菜・副菜の3カテゴリすべてに該当があれば+25点
  • ジャンクフード減点: ジャンクフード関連キーワード(ジャンク、カップ麺、ケーキ、揚げ物など)が含まれるたび-15点
  • 合計を0〜100にクランプ
  • メモが空(または空白のみ)の場合は無条件で0点

5.5 スコアラベル

スコアラベル
80以上絶好調
60〜79順調
40〜59まずまず
39以下要改善

6. コメント(アドバイス)機能

記録ごとに、歩数・睡眠・体重・食事の4項目すべてについてコメントを生成する(良好なら賞賛、不足なら改善提案)。各項目のスコア帯(80以上/60以上/それ未満)によって文面が変わり、食事コメントは不足カテゴリ(主食/主菜/副菜)やジャンクフードの有無を具体的に指摘する。

7. 主要フロー

7.1 記録の追加

  1. 「記録を追加」タブでフォームに入力(Enterキーで次の入力欄へフォーカス移動、フォーム送信はしない)
  2. 送信すると、同じ日付の既存記録があれば上書き、なければ新規追加
  3. 保存直後、結果画面(スコア・4項目コメント・前日比)を表示
    • 前日比は「暦日ベースの前日」(実際に前日の記録がある場合のみ差分を表示)
  4. 「記録一覧へ」ボタンで一覧画面に遷移

7.2 記録の編集

  • 一覧から「編集」を押すとフォームに値が入り「記録を追加」タブへ遷移
  • 更新後は結果画面を経由せず、直接一覧に戻る

7.3 プロフィール設定

  • 入力するたびに自動でstate更新・保存(localStorageモードは即時、API保存モードはデバウンス。7.6参照)
  • 加えて明示的な「保存する」ボタンがあり、押すと「✓ 保存しました」を2.5秒間表示

7.4 記録の推移グラフ

  • 指標切り替え: スコア / 体重 / 歩数 / 睡眠 の4指標をボタンで切り替え
  • 期間切り替え: 週(直近7日) / 月(直近30日) / 全期間。日付ベースでフィルタする(初期表示は「スコア×月」)
  • 縦軸は指標ごとに最適化: スコアは0〜100固定、歩数・睡眠は0起点、体重はデータ範囲(+適正体重)にズーム
  • 体重表示時は、プロフィールから適正体重が算出できる場合に破線の基準線を表示
  • 横軸の日付ラベルは最新日を基準に最大8個へ間引き、点のホバーで「日付: 値+単位」をツールチップ表示
  • 選択中の指標で値のある記録が2件未満の場合はグラフの代わりに案内文を表示

7.5 バックアップ(エクスポート/インポート)

  • エクスポート: profile + records + エクスポート日時をJSON化し、Blob / URL.createObjectURL を使ってファイルダウンロード(health-app-backup-YYYY-MM-DD.json)
  • インポート: <input type="file"> で選択したJSONを FileReader で読み込み、パース後に records / profile をまるごと置き換え(既存データは上書き)。API保存モードでは PUT /api/import でサーバー側も全置換する
  • localStorage版でエクスポートしたJSONをAPI版でインポートすることで、モード間のデータ移行ができる

7.6 API保存モードのデータ同期

  • 初回マウント時に GET /api/records と GET /api/profile を並列取得
  • 保存・削除は楽観的更新: 先に画面のstateを更新し、裏でAPIを呼ぶ。失敗時はアラートを表示してサーバーから再取得し、画面を実状態に合わせ直す
  • プロフィールは入力のたびに保存せず、変更が800ms落ち着いてから PUT /api/profile(デバウンス)。「保存する」ボタンは即時保存

8. バックエンドAPI (server/)

Express製のREST APIサーバー。環境変数 DATABASE_URL でPostgreSQLに接続し、起動時にスキーマを自動作成する。

メソッドパス役割
GET/api/healthヘルスチェック({"ok":true})
GET/api/records記録の一覧を日付昇順で返す
PUT/api/records記録の保存。id でupsertし、日付が他の記録と重複する場合は409
DELETE/api/records/:id記録の削除。存在しない場合は404
GET/api/profileプロフィール取得(未設定時は空文字のオブジェクト)
PUT/api/profileプロフィール保存(単一行にupsert)
PUT/api/import記録・プロフィールの一括置換(トランザクション内で実行)
  • CORS: 環境変数 ALLOWED_ORIGINS(カンマ区切り)で許可オリジンを指定
  • 認証(任意): 環境変数 API_TOKEN を設定すると、書き込み系(GET以外)に Authorization: Bearer <token> を要求する。未設定時は認証なし
  • エラー: 業務エラーは4xx + {"error": "..."}、想定外は500(詳細はサーバーログのみ)

9. 非機能・制約事項

  • データの保存範囲: localStorageモードではブラウザ単位(端末・ブラウザが変わるとデータは引き継がれない)。API保存モードではサーバーのDBに保存され、どの端末からも同じデータになる
  • シングルユーザー前提: ユーザーアカウントの概念はなく、DBは全利用者で共有される(API_TOKEN 未設定時は誰でも書き込める)。個人利用・デモ用途を想定
  • 公開構成: フロント=GitHub Pages(.github/workflows/deploy.yml。リポジトリ変数 VITE_API_BASE_URL でAPI接続先を注入)、API=Render(render.yaml)、DB=Neon。Renderの無料プランは15分無アクセスでスリープし、復帰に数十秒かかる
  • 食事評価の限界: キーワードマッチによるヒューリスティックであり、実際の栄養価・分量を評価するものではない
  • 年齢: プロフィールに保持するが、現バージョンのスコア計算には使用していない
